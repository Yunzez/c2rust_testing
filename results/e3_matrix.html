Not how much we cover — how deep we hit

Plain fuzzing covers the same code, so breadth showcases nothing. E3 measures depth: how many times each translated Rust function is exercised by the tool's own validation versus by our differential fuzz. The tools declare a translation correct on a handful of samples; that thinness is why bugs survive — and why we find the ones their validation missed.

Why depth, not breadth

The coverage-% framing died to one objection: plain fuzzing covers everything too, so a high coverage number highlights nothing. Correct — so E3 does not report coverage. It reports the per-function hit count and compares it against the tool's or library's own validation. The claim is causal, not tautological:

Existing translation validation is shallow — the tests a tool used to call a function "correct" hit it O(1)–O(10) times. Our differential fuzz hits it O(10⁴–10⁵) times. That depth gap is why bugs survive into shipped translations and why we find them.

Illustrative — the SACTOR fft baseline (6 samples) is real; our-fuzz bar is the target the census will measure.

What E3 lets us say

Our bug hunt exercised each function far deeper than the validation the tools used to declare correctness; over the fuzzable code we have differential-equivalence evidence (C ≡ Rust except the E1 bugs); we exercise ≥ the library's own shipped tests. The negative space is credible, not shallow.

What it does NOT say

Not "X% of the code is correctly translated" (coverage ≠ correctness — it bounds the scope of the claim, no more). And it does not showcase the matcher: plain fuzzing reaches the same code, so depth-vs-their-tests is the point, not breadth.

Method prototype — fft_crust anchor

Not one of the ten rows (a SACTOR test example) — used to prove the pipeline end to end and to anchor the "shallow validation" number. SACTOR validated the whole fft program with 6 test samples (inputs '' '12' …, varying one size scalar), so each of its 8 internal functions is hit only a handful of times by the tool's own correctness check. Everything is in place — buildable crate, the 6 baseline samples, the C oracle — to produce the per-function base-depth vs our-depth table the grid uses.

Mechanism = llvm-cov, no instrumenter: build once with -C instrument-coverage; run the baseline tests and our fuzz corpus separately; each llvm-cov export gives a per-function entry count = the hit depth. Diff the two.
