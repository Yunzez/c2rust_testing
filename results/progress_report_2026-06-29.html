0 · 项目定位 / 三个贡献

我们做的是 C→Rust 翻译正确性的差分测试。三个贡献,每一个都正好补上最近竞品(Fluorine arXiv:2405.11514;RustAssure ASE'25)明确承认但未解决的缺口:

贡献是什么竞品的缺口
C1 名无关 matcher当翻译改名/重构时,从结构(IO 形状、算子、调用图)恢复 C↔Rust 函数对应两家都靠名字配对(Fluorine 甚至强制译文保名,承认不保名 oracle 就崩)
C2 UB-正确的差分只在 C 里良定义的输入上把发散算作 bug(in-loop UB-free gate)两家都不做 UB 过滤;RustAssure 在 threats 里原话承认"内存损坏→假阳性"
C3 frontier 选点静态风险模型,挑哪些函数/边界值得 fuzz、哪些不可测并解释原因Fluorine fuzzer 脆(31 函数只 10 个存活);RustAssure 符号执行 5-15h、≤600 行天花板

0.5 · 领域分类:生成器 vs 比较器(intro 框架,paper 用)

这个领域有两大 body of work,intro 必须先把它讲清楚,我们才能定位自己:

Body干什么成员
A. 生成器 / 翻译器C → Rust,产出译文c2rust(机械)、Laertes/CROWN(规则式 lift)、C2SaferRust/SACTOR/RustMap/EvoC2Rust(LLM)、以及 Fluorine/RustAssure 内嵌的 LLM 调用
B. 比较器 / oracle判定 (C, Rust) 是否等价 / 找 bugFluorine(差分 fuzz)、RustAssure(差分符号)、我们

我们属于 B 类。

关键事实:Fluorine / RustAssure 是"生成器 + 比较器"捆死的端到端系统,且只测自己生成的译文

它们的"生成器"测试对象对第三方翻译器
Fluorine自调 5 个 LLM(GPT-4o/Claude/Gemini/Mixtral,temp 0.2,跑 3 次)翻译 7 个 OSS / 408 函数自己刚生成的译文c2rust 仅作"idiomatic 程度"参照,非被测对象
RustAssure自调 GPT-4o 等翻译 5 库 / 176 函数自己生成的译文CROWN/Fluorine 作对比基线,非被测输入
核心论点(intro 主线): 前作把比较器和某个自家 LLM 生成器捆死,因此继承了那个生成器的命名/形状约定——Fluorine 在 prompt 里强制译文保名,RustAssure 按名配对,因为它们控制生成端。代价是它们的 oracle:
  ① 用不了广义译文(c2rust / CROWN / idiomatic LLM / 人工 port——尤其改名/重构的);
  ② 对 UB 视而不见(把 C 未定义输入上的发散误报成翻译 bug)。
我们是生成器无关(generator-agnostic)的独立比较器——把比较器从生成器解耦。这正是三个贡献的统一动机:C1 解耦命名、C2 解耦 UB 假阳性、C3 解决规模。

1 · 起点:第一个真 bug(motivating example)

上一阶段在 Tulip Indicators(104 个数值指标)上,用一个手写的差分 harness 找到 C2SaferRust 发表译文里的真 bug:ti_adx_start 漏了一个解引用。本期把它做成了铁证的四路归因。

// 原始 C —— 正确
int ti_adx_start(TI_REAL const *options){ return ((int)options[0] - 1) * 2; }   // 读 options[0](周期)

// c2rust —— 正确(保留 *)
pub unsafe extern "C" fn ti_adx_start(options: *const c_double) -> c_int {
    return (*options.offset(0) as c_int - 1) * 2; }

// CROWN(规则式安全 lift) —— 正确(保留 *)
pub unsafe extern "C" fn ti_adx_start(options: *const c_double) -> c_int {
    return (*options.offset(0) as c_int - 1) * 2; }

// C2SaferRust(LLM 安全 lift) —— 错!漏了 *
pub extern "C" fn ti_adx_start(options: *const f64) -> i32 {
    unsafe { (options.offset(0) as i32 - 1) * 2 } }   // 把指针地址转 i32!返回常量垃圾

四路差分结果(seed 1,3000 次/指标,reltol 1e-9):

翻译方法buggy 指标
c2rust机械转译0 ✓
CROWN规则式所有权 lift(无 LLM)0 ✓
C2SaferRustLLM 安全 lift1 ✗ (adx)

意义:把 bug 精确归因到 LLM 改写步骤,而非"安全 lift 本身有风险"——机械转译 ✓ + 规则式 lift ✓ + LLM lift ✗。CROWN 在此是归因对照。

2 · 方法论关:harness 必须自动生成

关键的一刻:Tulip 那个 harness 是手写的(只因 Tulip 104 个函数共享统一 ABI)。靠人手写 harness 不是科学方法,reviewer 会砍。 我们其实有自动生成器 tools/stu_selector/gen_diff_harness.py(~1000 行):

  • 用 libclang 解析 C 签名 → 自动推断每个参数的角色/形状(scalar、input_buffer、output_array、out_scalar…)
  • 自动 emit 一个 cargo-fuzz 项目:C 编成 oracle(f→c_f,sancov 插桩),译文当 lib crate,按角色把 fuzz 字节解码成参数,调 c_<entry> 和 translated::<entry>,不一致就 panic
  • 名配对(c2rust 保名)用 mapping.py;改名用 matcher.py(C1)

生成的差分核心(含 UB 门):

use clip_gpt4o as translated;
extern "C" { fn c_clip(a: i32, amin: i32, amax: i32) -> i32;
              fn c2r_ub_reset(); fn c2r_ub_get() -> i32; }
fuzz_target!(|data: &[u8]| {
    // ... 从 data 解码 a, amin, amax ...
    c2r_ub_reset();
    let c_ret = c_clip(a, amin, amax);
    if c2r_ub_get() != 0 { return; }   // C 命中 UB → 拒绝该输入(C2 的关键)
    let r_ret = translated::clip(a, amin, amax);
    if c_ret != r_ret { panic!("divergence: return value"); }
});

4 · UB 门双向例证(核心创新 C2)

这是相对 Fluorine/RustAssure 最硬的差异点——它们都不做 UB 过滤。我们用同一套 harness 在两个真实 LLM 译文上给出正反例:

反例:UB 门压掉假阳性 — sign_extend

sign_extend(val, bits) 算 shift = 32 - bits。当 bits=0 时 shift=32,C 的 val<<32 是 未定义行为(契约外输入)。gpt4o 译文在此 panic。

运行结果
门开(--ub-free)13.7M runs,CLEAN(UB 输入被拒,所有良定义输入两边一致)
门关DIVERGENCE:Rust attempt to shift left with overflow panic

→ 门关 = 假阳性(没 UB 过滤的 oracle 会误报成翻译 bug);门开 = 正确判无 bug。

正例:UB 门保留真 bug — u8encode_

RustAssure 报的 u8c bug。buggy 译文(GPT-4o)无守卫:

fn u8encode_(ch: i32, s: Option<&mut [u8]>) -> i32 {
    let mut len = -1;
    // ... ch 在各 Unicode 区间才设置 len ...
    s[len as usize] = 0;   // 无守卫!ch 超范围 → len=-1 → s[usize::MAX] → panic
    len
}

而 C 在 ch 超 Unicode 范围时良定义:返回 -1、只写 *s='\0'。C 无 UB → 我们的门保留这个 panic = 复现 RustAssure 的 bug,且证明是真 bug 不是 UB 假阳性。

合起来: 两个真实译文,一正一反 —— 门压掉 sign_extend 的假阳性,保留 u8encode_ 的真 bug。UB 门两面都成立 = C2 的完整论证。

5 · idiomatic C-ABI bridge(自动 harness 的"硬骨头")

竞品强制译文保 C-ABI(或降到 LLVM IR)来回避类型鸿沟。我们要直接调 idiomatic 译文,所以扩展了生成器:解析译文实际签名,把同一份解码字节 marshal 成 C 端要的裸指针 + Rust 端要的 idiomatic 类型。

// 同一份 buffer,两边各取所需形状:
let c_ret = c_aptx_bin_search(value, factor, intervals_buf.as_ptr(), nb_intervals);            // C-ABI 裸指针
let r_ret = translated::aptx_bin_search(value, factor, &intervals_buf.clone().into_boxed_slice(), nb_intervals); // ← 自动 marshal 成 &Box<[i32]>

已支持的映射:

Rust 参数类型自动生成的调用
*const T(c2rust / gpt4o 裸指针)buf.as_ptr()
&Box<[T]>&buf.clone().into_boxed_slice()
&[T] slice&buf[..]
Vec<T> / &Vec<T>buf.clone() / &buf.clone()
Option<&mut [T]>(输出缓冲)Some(&mut buf[..])

6 · 相关工作 / 工具版图(本期摸清)

没有更 SOTA 的纯 static 工具能替代 CROWN

c2rust→Laertes('21)→CROWN('23) 这条纯 static 线 2023 年就停了,2024-26 全转向 LLM/hybrid。新的 static 工具都很窄(Forcrat=只管 I/O、GenC2Rust=只管 void*、Concrat=只管锁)。所以 CROWN/Laertes 仍是仅有的通用 static baseline——这反过来说明不必再为 CROWN 多投入。

7 · CROWN 语料 + 一次"撞墙"的诚实记录

试图把 CROWN 跑到中立的 CRUST-bench 上(让它当 baseline),撞上版本墙:CROWN 的 rewriter 和它确切的老 c2rust 版本死绑。

  • 本机 Ubuntu 26.04 装不了 LLVM 15 → 用 docker(ubuntu:22.04)从 git tag 编了 c2rust 0.17/0.18
  • 用 CROWN 的确切 flags(--reduce-type-annotations)后,单函数编译错误从 26 → 3,但 clean-compile 封顶在 12/87(残留 1 个指针的 over-lift 差异)
  • 诚实发现(可写进论文):CROWN 不是一键工具——它作者自己的 run.sh 对 genann/quadtree/lil 都逐程序调不同 flag
  • 决定:收手。 CROWN 是 ~0-bug 的对照工具,中立 12 + 它自带 benchmark 19 = ~31 个程序,够用

附:也踩了 LibAFL 的坑——它的 libfuzzer shim 在本环境忽略 -max_total_time/-timeout、能在某输入上死循环 4.5 小时。换成真 libfuzzer-sys = "0.4" + 把 C oracle coverage 从 trace-pc-guard 改成 inline-8bit-counters,pc-table,trace-cmp 后解决,现在 ~50 万 exec/s、正常响应超时。

E · Evaluation 设计(FSE 严谨版 · paper 用,核心)

投 FSE,比较器类工作的严谨核心是:怎么证明一个 bug-finding oracle 又准(precision)又全(recall)。组织成 5 个 RQ,每个对应一个贡献或竞品对比。

研究问题(RQ)

RQ问题对应主指标
RQ1能在真实、已发表的译文里找到真 bug 吗?有效性确认 bug 数(人工 + root-cause),跨多个生成器
RQ2UB 门把假阳性降了多少?(门开 vs 门关消融)C2假阳性率;门压掉的 UB 诱导发散 delta;precision
RQ3能测改名/重构的译文吗?(按名 oracle 在此失效)C1matcher precision/recall vs ground-truth 映射
RQ4vs Fluorine & RustAssure(共享 benchmark)对打bug 数 / 假阳性 / 可处理函数比例
RQ5frontier 选点准不准 + 规模/吞吐C3safe/risky precision(G2/G3)、exec/s、找 bug 墙钟

语料矩阵:生成器 × 数据集(中立,不自造)

我们不自己造翻译器当 headline(破"射箭画靶")。在第三方中立数据集上测多个已发表生成器的产物:

生成器(Body A)命名用于

CROWN保名RQ1/RQ2 规则式 lift 对照
C2SaferRust / SACTOR多数保名RQ1 LLM bug 来源
raw LLM(我们跑)+ 人工 port改名/重构RQ3 matcher 主场
数据集规模角色

Ground truth 怎么来(规模化 precision/recall 的关键)

不能全靠人工标注。三个来源叠加:

  1. 已报 bug:RustAssure 的 16 个(bug_description.csv)= 已知正例,直接 cross-validate。
  2. 变异注入(mutation):对正确译文注入已知语义变异(漏解引用、改边界、换运算符、off-by-one)→ 受控正例,算 recall。这是"针对翻译 oracle 的 mutation testing",规模化且 reviewer 认可。
  3. 人工 port 映射:CRUST-bench 自带的人工 Rust 接口 = 真实人写的改名/重构译文,带人工 C↔Rust 对应。用作 RQ3 matcher 的 ground-truth 映射。(样本量大;且数据公开,结论可复核、无可指摘。) 另有 SACTOR 自带的 function_name_map.json 作第二来源。

消融(必做)

  • UB 门 on/off(RQ2 核心):同语料同 seed,门关报的发散 − 门开报的 = UB 诱导假阳性。已有正反个例:sign_extend(门压假阳性)、u8encode_(门保真 bug)。
  • matcher on/off(RQ3):按名配对 vs 名无关 matcher,在改名译文上 → 名配对的失配率 = matcher 的增量价值。
  • frontier on/off(RQ5):全 fuzz vs 只 fuzz 选中边界 → 找 bug 效率 / 假发散对比。

对打协议(RQ4,vs Fluorine & RustAssure)

  • 共享 benchmark = libopenaptx(两家都用过,我们有双译文)。三方同跑同一批 (C, Rust)。
  • 报三栏:① 各自找到的 bug、② 各自的假阳性(我们有 UB 门、它们没有 → 预期我们更干净)、③ 能处理的程序/函数比例(Fluorine fuzzer 31 个活 10 个;RustAssure ≤600 行 + 5-15h/库)。

Threats to validity(必写)

  • fuzzing 不完备:等价是启发式 → 报 coverage + 预算(学 Fluorine "5 分钟、97% 行覆盖")。
  • ground-truth 标注:人工确认的样本量、root-cause、可能的 inter-rater。
  • 泛化:语料/生成器选择偏差;变异算子的代表性。
  • UB 判定:UBSan/ASan 覆盖的 UB 类别有限(明示哪些 UB 被门到、哪些靠 frontier 静态避开)。
一页纸总结(给 paper): 我们是生成器无关的差分比较器。RQ1 证有效(跨多个已发表生成器找到真 bug),RQ2 证精度(UB 门消融,降假阳性——竞品没有),RQ3 证广度(名无关 matcher 测改名译文——竞品做不到),RQ4 证优于现有 oracle(libopenaptx 三方对打),RQ5 证规模(frontier + 吞吐)。Ground truth = 已报 bug + 变异注入 + 人工 port,全部公开可复核。
