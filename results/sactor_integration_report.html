0 · 背景：SACTOR 是什么，我们为什么用它

SACTOR (Structure-Aware C To Rust translator, arXiv 2503.12511) 是一个真实发表的 C→Rust 翻译框架， 不是单次 prompt。它分两阶段：先 unidiomatic（c2rust 风格、repr(C)、裸指针），再 idiomatic（slice/Vec/Option，符合 Rust 习惯）。 我们用它替换掉之前那个「自己编的单次 prompt 翻译器」，作为产出 重命名/重构译文 的可信来源 —— 这正是我们 name-independent matcher 要对付的对象。

关键认知 —— SACTOR 没有 fuzzing。 它的「等价性验证」是函数替换 + 重跑你给的几个样例测试： 把某个函数的 Rust 译文用 FFI 暴露成 C 符号、挖掉原 C 函数、链接进去、重跑 test samples。 这是 example-based，不是覆盖率引导，也不感知 UB。
→ 这恰好是我们差分 fuzzing 的补位空间：SACTOR 的「已验证」只在它那几个样例上成立，函数可以通过 SACTOR 却在样例之外跟 C 分叉。我们 = 在它验证不到的地方做强验证。

1 · 我们踩的坑与解法 全部已解决或绕过

从「在真实语料上跑 SACTOR 出 idiomatic Rust」到成功，依次遇到的问题：

  • 缺 valgrind 阻断
    SACTOR 启动即报 OSError: Missing requirements: valgrind。
    解法： apt-get install valgrind。
  • lib 模式是死路 绕过
    纯库（如 bitset）走 --type lib 连环受阻：① 要 --executable-object； ② 带 compile_commands.json 时严格 link-closure 把编译器内建 __builtin_popcount 当成「未解析的 C 函数」报错； ③ generate-tests --type lib 直接 NotImplementedError("Library test runner not implemented yet")； ④ 逐函数 FFI 验证 harness 需要一个来自样例的 main，空样例 → undefined reference to `main`。
    解法： 放弃 lib，改走成熟的 bin 模式 —— 给库加一个确定性的 main 驱动，当成程序翻译。
  • 编译器内建 & static 链接 已解决
    __builtin_popcount/__builtin_parity/__builtin_clz 被 SACTOR 依赖追踪当成「应先翻译的函数」→ RuntimeError； 而 static inline 辅助函数不在符号表里 → 逐函数 FFI 验证链接失败。
    解法： 用纯表达式替掉内建（见下方 PARITY8）、把辅助函数去掉 static。
  • FILE* → _IO_FILE 编不过 已解决
    bitset 的 fopen/fread 经 c2rust 译出 glibc 内部类型 _IO_FILE，Rust 侧编译失败。
    解法： 选择/裁剪出不含文件 I/O 的纯逻辑函数。
  • gpt-4o 太弱 换模型
    SACTOR 默认 gpt-4o，unidiomatic 只成功 7/13（连 new/count/test 都译不出）；gpt-5.1 则 13/13。
    解法： 配置文件锁定 gpt-5.1。
  • SPEC 解析 bug（我们修了 SACTOR） 已修复
    idiomatic struct 翻译要求 LLM 同时输出 ----SPEC---- JSON 块。SACTOR 的正则强制要求结尾有横线， 而 gpt-5.1 输出 ----END SPEC（无尾横线）→ 报「SPEC block not found」。这是模型格式跟从习惯与 SACTOR（按 gpt-4o 调）的错配。
    解法： 放宽正则容忍尾横线缺失（最小、可上游的鲁棒性补丁，见下方 diff）。
  • 位压缩 struct 撞上 SACTOR 建模局限 SACTOR 局限，换目标
    bitset 是位压缩结构：数组字节数 = (size+7)/8 ≠ size。 SACTOR 的 struct 验证假设「长度来源字段会被 Vec::len() 取代而消失」，于是把 size 当派生字段， 和必须保留的 size 撞车 → error[E0062]: field `size` specified more than once。
    判断： 这是 SACTOR 对位压缩 struct 的真实建模缺陷，不是我们的 bug；再钻就是「补窟窿」。
    解法： 换一个标量/无 struct 的目标（FastHamming）。

2 · 成功跑通：FastHamming（Hamming 纠错码）

换到 CRUST-bench 的 FastHamming（5 个函数，纯 uint8 整数，无 struct）后， 配方完整跑通：自包含 C + 确定性 main 驱动 → generate-tests（LLM 合成并验证 6 个样例）→ translate --type bin。 SACTOR 输出 EXIT=0，idiomatic 全译出，clippy 0 warning / 0 error，所有测试通过。

翻译前后对比 · 这是货真价实的 idiomatic 重构

函数原始 C 签名SACTOR idiomatic Rust 签名
hecc_encode bool (const uint8_t*, size_t, uint8_t*, size_t*) fn (&[u8], &mut [u8]) -> Option<usize>
hecc_decode_impl bool (const uint8_t*, uint8_t*, size_t) fn (&[u8]) -> Option<Vec<u8>>

4 个 C 指针/长度参数 → 2 个 slice；bool + 出参 → Option。函数名 SACTOR 保留了（故 ground truth = 恒等名映射），但 io-shape 天差地别 —— matcher 必须靠结构而非名字配对。

原始代码 · idiomatic 译文片段（hecc_encode）

pub fn hecc_encode(inbuf: &[u8], outbuf: &mut [u8]) -> Option<usize> {
    fn checked_mul(a: usize, b: usize) -> Option<usize> { a.checked_mul(b) }   // ← 嵌套 helper
    let insize = inbuf.len();
    let max_insize = checked_mul(usize::MAX >> 4, 15)?;
    if insize > max_insize { return None; }
    let blocks = (insize + 14) / 15;
    let reqsize = checked_add(blocks, insize)?;
    if outbuf.len() < reqsize { return None; }
    let mut in_pos = 0; let mut out_pos = 0;
    while insize - in_pos >= 15 {
        let in_chunk = &inbuf[in_pos..in_pos + 15];
        let out_chunk = &mut outbuf[out_pos..out_pos + 16];
        hecc_encode_impl(in_chunk, out_chunk);
        in_pos += 15; out_pos += 16;
    }
    ...
    Some(out_pos)
}

结论： ① matcher 在真实 transpiler 输出上是有效的 —— 签名从 C ABI 被重构成 idiomatic slice/Option，它仍 100% 靠结构配对成功。这是「不只在合成 c2rust 上过拟合」的真外部验证。
② 那 50% 不是 matcher 的锅，而是 Rust analyzer 把嵌套局部函数拍平进了候选集：SACTOR 把 parity8 / checked_add / log2uint8(嵌套) 等 helper 内联进 idiomatic 函数体，analyzer 当顶层节点发出来 → 干扰项偷走真匹配，还触发了顶层/嵌套 log2uint8 重名（即我们一直记着的 hir-id 隐患，这次实地观测到了）。

4 · 扩面：5 个 CRUST-bench 程序的批量结果

为看 matcher 在真实 transpiler 输出上面上的表现，挑了一批不同规模的 CRUST-bench 程序（故意偏指针密集）， 按已验证的 bin 配方各跑 SACTOR idiomatic → matcher（用 SACTOR 自带的 name map 当 ground truth）。

程序函数数SACTOR idiomaticmatcher 准确率说明
FastHamming5✅ 成功6/6 (100%)纯值函数
fft7✅ 成功8/8 (100%)SACTOR 把 C 宏展开成 11 个嵌套 helper，被新过滤器全部正确剔除
amp5❌ 失败—char* buf 游标：返回借用 slice + buf+=len，借用检查不可表示
gfc7❌ 失败—函数 F 依赖的 GFC 指针数组结构（长度派生自字段 r）未注册
utf813❌ 失败—idiomatic 又慢又栽在 make_utf8_char_iter；含 main 的合成驱动也撞 uint32_t 导入
三个核心发现：
① 两个成功例 matcher 都 100% —— 既验证 matcher 在真 transpiler 输出上有效，也验证了上一节那个嵌套排除修复（fft 的 11 个宏展开 helper 全被正确过滤，否则会像最初 hamming 那样掉到 50%）。
② 两个成功例的 name map 都是恒等 —— SACTOR 不改函数名。 所以这些验证的是 io-shape/结构鲁棒性，不是抗重命名。matcher 抗重命名的主场必须是裸 LLM / 人写移植（无 map、真改名）。
③ SACTOR 的 idiomatic 阶段对真实指针密集 C 很脆弱 —— 只有"纯值函数、无指针游标、无指针数组结构"的程序能过（本批 2/5）。失败都是真实的 Rust 习惯化极限（游标指针、字段派生长度的数组），不是我们能修的。
对路线的含义： SACTOR 作为 matcher 的外部验证源偏薄 —— 能跑通的程序少、且不改名。 这反而强化了定位：matcher 真正的主场是无 map 的重命名场景（裸 LLM 直翻、人写 Rust 移植）。 下一步要么转向裸 LLM 直翻线，要么评估第二个框架 C2SaferRust；若框架普遍跑不动真实程序，可能需要自建 benchmark。

工程副产品：--continue-run-when-incomplete 应进默认配方（合成 main 这类 scaffolding 失败时不拖垮全局）；translate 超时设 ≥900s（595s 把 fft 在最后 10 秒杀了）；SSE 内联（clhash）、递归结构（cJSON）预先排除。

5 · 接下来的步骤

✅ 已完成：Rust analyzer 排除嵌套/局部函数

已在 analyzer/src/lib.rs 实现（祖先含另一个 ast::Fn = 局部函数，标 nested_local 排除，调用边由父函数递归遍历保留）。 hamming 现在开箱即 6/6（不再需要手动过滤），fft 的 11 个宏展开 helper 也被自动剔除；lil 回归门仍 PASS（126/128）。 C 没有嵌套函数，这些局部 helper 也没有 C 对应物 —— 排除它们让真实语料的匹配从一开始就干净。 信号很清晰：顶层 = col-0 的 pub fn；嵌套 = 函数体内的 fn，rust-analyzer 的 HIR 知道父作用域。 改完用 lil 回归门（128 函数 / 55 个同形 fnc_*，门槛 126/128）把关，确保不回退。同时顺手把那个 hir-id 重名隐患一并处理。

▶ 然后：扩面跑更多 CRUST-bench 程序

按已验证的 bin 配方，挑函数多、标量/简单 struct 的真实程序（如 fft、其它算法库）多跑几个， 得到一张「matcher 在真实 SACTOR 输出上的准确率」表 —— 这是论文里外部验证那一节的数据。

▶ 之后：把差分 fuzzing 接到 SACTOR 译文上（主线收口）

这是整件事的终点：matcher 配好 C↔Rust 对 → 我们的 覆盖率引导 + UB-free gate 差分 fuzzing 去 SACTOR 样例之外猛打。 找到分叉 = SACTOR 的样例验证给了假信心（强结果）；找不到 = 独立佐证。FastHamming 是纯整数、确定性，正是理想的第一个 fuzzing 目标。

▶ 平行：第二个框架 C2SaferRust

为扩大 benchmark 规模，C2SaferRust 早晚要上 —— 但它需要工具链手术（pin nightly-2022-08-08 的 rustc_private slicer、无单文件入口）。优先级排在上面三项之后。
