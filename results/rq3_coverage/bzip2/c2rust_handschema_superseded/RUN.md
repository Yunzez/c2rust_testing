### 64 → 14

Every rejection carries the generator's own message. By cause: **31** a parameter is a pointer to a
struct carrying pointers (`EState*`, `DState*`, `bz_stream*` — "needs invariant reconstruction");
**12** `BZFILE*`/`FILE*` process-owned state; **4** `UInt16* quadrant` with no length parameter;
**2** `void* opaque`; **1** `BZ2_bzlibVersion` takes no parameters.

### 14 → 11

`BZ2_bzopen`, `BZ2_bzdopen` and `bzopen_or_bzdopen` return `BZFILE*`. The harness will not compile
because the comparator cannot compare two heap pointers from two different allocators.
**The eligibility rule inspects only parameters, never the return type** — a real gap, and these
three are the same file-opening family the parameter rule rejects elsewhere.

## 2. What round 1 got wrong

Round 1 ran 7 harnesses for 4543 s and reported 0.621 function / 0.481 region coverage. Six of
those seven harnesses could not construct a valid input:

- **`dest` was a single stack `i8` and `destLen` was always 0.** bzip2 reads `*destLen` as the
  output *capacity*, so `BZ2_bzBuffToBuffCompress` returned `BZ_OUTBUFF_FULL` on every input and
  never wrote a byte. The schema layer names the role `output_buffer` with a `capacity_param`, but
  `items_from_schema` downgraded it to the `inout_buffer` decode ("the richer semantics are
  deferred").
- **Input buffers were capped at 63 elements** by a hardcoded `% 64` in the generated byte cursor,
  so `nblock < 10000` always held and `BZ2_blockSort` never left the fallback sorter
  (`blocksort.c:1044`). `mainSort`, `mainQSort3`, `mainSimpleSort` and `mainGtU` were unreachable
  *by construction*.
- **Fixed output arrays were capped at 64**, smaller than every table bzip2 indexes
  (`cftab[257]`, `base[length[i]+1]` up to 257, `code[alphaSize]` up to 258) — the cause of the
  heap overflows that gave `BZ2_indexIntoF` and `fallbackSort` empty corpora.
- **Scalars were unbounded.** bzip2 validates every one (`blockSize100k` 1..9, `verbosity` 0..4,
  `workFactor` 0..250, `small` 0..1, `maxLen` ≤ 23, `alphaSize` ≤ 258), so a random `i32` was
  rejected at the parameter check with probability ≈ 1.
- **`bounded_scalar` used `%`, which keeps the sign of the dividend**, so a scalar declared 1..9
  actually ranged −7..9 — half of a campaign spent on inputs the callee refuses.

Only `mmed3` (three scalars, pure) was correct.

## 3. Fixes, all in a scratchpad copy (repo copies untouched)

Diffs: `raw/generator_rq4_fixes.diff`, `raw/schema_module_rq4_fixes.diff`.
`GEN_VERSION 0.5+rq4fix2026-09-03b`.

Round 1 (needed before any real library could run at all):
1. **C globals were not renamed in the oracle.** Only functions were. `BZ2_crc32Table` and
   `BZ2_rNums` exist in both the C oracle and the translation, so un-renamed they collapse onto one
   storage location and the differential compares a value with itself. The linker happened to
   reject it here; that was luck.
2. **The return type was not typedef-resolved**, so a `UChar`-returning function got an `-> i32`
   extern declaration — on x86-64 the upper 24 bits of a byte return are unspecified.

Round 2 (the input model):
3. **`output_buffer` completed, with a new `capacity_ptr` role** — allocate to the schema's `cap`,
   pass the capacity by pointer seeded with that allocation, and compare the written length plus
   the `dest[..written]` prefix (never the tail the callee did not write).
4. **`max_len` plus a new `take_rest_*` cursor method**, replacing the hardcoded 63-element cap.
5. **`--schema PATH`** — `schemas/<program>.json` is keyed to one entry; a library needs one per
   boundary.
6. **`decode_scalars_first`** — otherwise every scalar's byte offset moves whenever a
   megabyte-sized buffer changes length. Call order is unaffected (decode comes from `items`, the
   call from `abi`).
7. **`bounded_scalar` uses `rem_euclid`**, not `%`.
8. Three validator gaps: `output_array` was not in the legal pointer-role set (so no schema could
   describe a fixed-cap output array, though the generator has always emitted them), `length` roles
   need `of_buffer`, and `observable_length` gained the `capacity_ptr_writeback` kind.

**Ten hand-authored schemas** (`schemas/`), one per runnable boundary, every constant justified by
a line of bzip2 1.0.8 (`raw/make_schemas.py` records the citations). Each is cross-checked against
the libclang signature by `validate_against_signature` before use, so a wrong annotation fails
loudly instead of generating a wrong harness.

**Seeds** (`seeds/`, `raw/make_seeds.py`): a harness input is a byte-cursor encoding, not a raw
file, so real payloads are wrapped in that format — 22 compress seeds (the distribution's own
`sample{1,2,3}.ref`, `words*`, C sources, long runs, all-same, random, and a just-over-10000-byte
block) and 30 decompress seeds (real `.bz2`, the shipped `sample*.bz2`, truncated and bit-flipped
streams). No other harness is seeded.

### Remaining limitations, declared

`BZ2_indexIntoF`'s `cftab` and `fallbackQSort3`/`fallbackSimpleSort`'s `fmap`/`eclass` have **no
length parameter**, so the schema language cannot express a faithful input for them: they get
memory-safe zeroed fixed-cap arrays with indices bounded to that cap. Their real coverage arrives
transitively through `fallbackSort` and the compress path. Recorded in each schema's `note`.

## 5. Coverage collection and the UB gate

`cargo fuzz coverage` rebuilds each harness with `-C instrument-coverage` and replays a snapshot
once per input, unmutated. The C oracle and the gate stay in the loop, so the Rust coverage
collected is by construction the coverage of inputs that passed the gate and reached Rust.

| harness | replayed | reached Rust | **excluded by the C-UB gate** | fns | regions |
|---|---:|---:|---:|---:|---:|

| BZ2_bzBuffToBuffDecompress | 438 | 438 | 0 | 13 | 2528 |
| **BZ2_hbCreateDecodeTables** | 58 | 54 | **4** | 1 | 83 |
| **BZ2_hbAssignCodes** | 46 | 44 | **2** | 1 | 26 |

**7 inputs were excluded by the C-side UB gate before Rust ran.** Measured as
*corpus size − execution count of the Rust entry function*; an earlier heuristic that read the
gate's own `return` arm out of the fuzz target's coverage was silently reading the byte-cursor
helpers (libfuzzer's `fuzz_target!` closure carries no separate record there) and always reported 0.
It was replaced, not reported.

Per-harness numbers are intermediate evidence. **Nothing is summed or averaged across harnesses** —
the artifact result is the union of function and region *identities*.

### What the set difference says

- **`only_tests` is 8 functions, and all 8 are the `FILE*`/`BZFILE*` stream API**
  (`BZ2_bzWriteOpen`, `BZ2_bzWrite`, `BZ2_bzWriteClose64`, `BZ2_bzReadOpen`, `BZ2_bzRead`,
  `BZ2_bzReadClose`, `BZ2_bzReadGetUnused`, `myfeof`) — exactly the boundaries the eligibility rule
  rejects for needing process-owned state. Reaching them requires an environment adapter, the
  deferred case in stage 3 of the method. **Not one of the eight is a boundary the validator drove
  and missed.** (In round 1 this set also held `mainSort`, `mainQSort3`, `mainSimpleSort` and
  `mainGtU`; those were an artifact of the 63-byte input cap and are now covered.)
- **`only_ours` is 2 functions but 409 regions** — the buffer-to-buffer entry points, which the
  shipped CLI never calls, plus the paths inside the library that only they reach.
- **`covered_by_neither` is 13**: the `FILE*` convenience layer (`BZ2_bzopen`, `bzdopen`, `bzread`,
  `bzwrite`, `bzclose`, `bzflush`, `bzerror`, `bzlibVersion`, `bzopen_or_bzdopen`,
  `BZ2_bzWriteClose`), `BZ2_bz__AssertH__fail`, `isdigit`, `__isctype`.

At **region** level the validator and the shipped suite are at parity (0.798 vs 0.797) while
reaching substantially different code — 409 regions only ours, 398 only tests. At **function**
level the validator is 9 points behind, and the whole gap is the eight stream-API functions it is
structurally unable to drive.

## 10. UB-gate ablation, and what the gap is actually made of

The generator now selects the C reference and the UB gate **at run time** (`C2R_MODE`,
`GEN_VERSION 0.5+rq4fix2026-09-03c`, `raw/patch_generator_v3.py`), so all three settings share one
binary, one coverage map and one identity space. Earlier a gate ablation would have needed a second
build, and three separate defects in this experiment came from exactly that kind of cross-binary
comparison. Every archived corpus stays valid because the input decoding is untouched.

The ten harnesses were replayed over the **same** archived campaign corpora in each mode
(`raw/run_modes.sh`, `raw/modes.py`, `ubgate_ablation.json`, `ubgate_mode_exports.tar.gz`):

| mode | C runs | gate | compared | functions | fn cov | regions | reg cov |
|---|---|---|---|---:|---:|---:|---:|
| `gated` (default) | yes | yes | yes | 45 | 0.682 | 7018 | 0.798 |
| `nogate` | yes | no | yes | 45 | 0.682 | 7018 | 0.798 |
| `rust-only` | no | no | no | 45 | 0.682 | 7018 | 0.798 |

**The gate withholds 0 functions and 0 regions.** The 7 inputs it rejects contribute no coverage
that other inputs do not already provide. Removing the C side entirely buys nothing measurable —
while costing the oracle, the divergence check and the whole attribution story.

Two self-checks, both passed and both recorded in `ubgate_ablation.json` rather than assumed:
`gated` reproduces the headline 45 / 7018 exactly, so adding the runtime switch changed no
measurement; and `nogate` and `rust-only` are identical set-for-set (0 symmetric difference in both
functions and regions), confirming the two sides do not interfere — executing C cannot change what
Rust executes.

`rust-only` coverage is reportable as a Rust-side number alongside the others; it is **not** a
validation result, because without the oracle no divergence can be detected.

### The gap is one missing capability

Of the 66 in-scope functions the validator covers 45. `uncovered_classification.json` classifies
the 21 it does not, with nothing left over:

| class | n | |
|---|---:|---|
| the `FILE*`/`BZFILE*` API itself | **17** | `BZ2_bzReadOpen`, `bzRead`, `bzReadClose`, `bzReadGetUnused`, `bzWriteOpen`, `bzWrite`, `bzWriteClose`, `bzWriteClose64`, `bzopen`, `bzdopen`, `bzread`, `bzwrite`, `bzclose`, `bzflush`, `bzerror`, `bzopen_or_bzdopen`, `myfeof` |
| reachable only through that API | **2** | `isdigit`, `__isctype` — called only from `bzopen_or_bzdopen`'s mode-string parsing |
| degenerate | **2** | `BZ2_bzlibVersion` takes no parameters, so no logical input exists; `BZ2_bz__AssertH__fail` calls `exit(3)`, so the boundary is not observable |

So **19 of the 21 missed functions sit behind a single missing capability — a model of
process-owned file state** — and the remaining two cannot be driven by any harness. The validator
covers every one of the 45 functions that is not behind a file handle.

This is exactly the deferred case in stage 3 of the method, and `BZ2_bzReadOpen(FILE *)` is the
example the workflow figure already uses. The measured gap is that example and nothing else.
