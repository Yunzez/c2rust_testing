# LLM-assisted input refinement: experiment plan

**Status:** draft for execution after the current RQ4 campaign chain finishes.

## 1. Purpose

The existing RQ4 experiment measures the reach of the fully automatic, deterministic harness
planner. Some cells enter nearly every translated function but cover little of the code inside
those functions. Tulip is the clearest current example: the harnesses construct the pointer tables
and enter 212 of 213 functions, but arbitrary `double` values rarely satisfy the small integer
domains expected by `options[]`.

This follow-up asks a separate question:

> When the automatic harness reaches a boundary but its byte decoder rarely enters the boundary's
> semantic domain, how much additional region coverage can bounded LLM feedback obtain?

The current results remain the **automatic baseline**. LLM-assisted results are an extension and
must never replace low baseline numbers. A low value caused by a translation failure or an
unsupported interface is also a result; refinement is intended only for value-distribution
problems.

## 2. Scope of the first version

The LLM may propose **semantic seed cases** for values that the existing InputPlan already
constructs:

* scalar parameters;
* a constant-index element of an existing scalar array, such as `options[0]`;
* boundary values and small finite sets derived from guards or conversions in the C body.

The LLM may not change:

* function matching;
* parameter roles, storage sizes, pointer extents, or ownership;
* producer or destructor selection;
* the Rust bridge;
* the comparison ladder or comparator plugins;
* the C or Rust implementation; or
* confirmation and defect-promotion rules.

This deliberately excludes construction failures such as PtrTrans's
`Option<&mut cJSON>` producer shape and failures caused by a translated constructor. Those require
new generator capabilities or constitute translation behavior; value hints cannot resolve them.

## 3. InputPlan and InputHints have different jobs

The generated harness and its decoder remain byte-for-byte unchanged. Hints affect only the
initial corpus: a deterministic seed materializer uses the InputPlan to encode semantic cases into
the byte layout consumed by the existing harness. LibFuzzer can then retain and mutate inputs that
begin inside the boundary's accepted domain.

For example, the `ti_sma` plan says that the byte stream decodes, in order, an integer `size`, one
row of 4,096 `double` input values, and one `double` at `options[0]`; the output row consumes no
bytes because the harness allocates and zero-fills it. A hint such as `(size = 64,
options[0] = 5.0)` therefore cannot simply be written at the start of a file. The plan-guided
materializer writes the bounded scalar representation, fills the input row deterministically, and
places the exact IEEE representation of `5.0` at the offset the decoder will read.

The generated `HarnessPlan` remains unchanged. Hints live in a separate, auditable
`InputHints` file. This keeps the distinction clear:

* `HarnessPlan` states what inputs can be constructed safely and how they cross the language
  boundary.
* `InputHints` states concrete semantic cases worth placing in the initial corpus.

This preserves the represented input domain exactly because the decoder is unchanged. An
incorrect LLM suggestion can produce an unhelpful seed, but it cannot remove an input, alter
storage, or weaken the oracle.

For the held-out comparison, every hinted seed has a size-matched control seed. Both are generated
from the same deterministic pseudorandom byte string; the hinted version overwrites only the
plan-resolved fields. The two conditions therefore start with the same number and sizes of inputs.

## 4. What already exists

The following pieces can be reused without changing their semantics:

| Existing component | Reuse in this experiment |
|---|---|
| `harness_plan.py` and archived `plans.json` | Parameter types, adapters, and source evidence |
| Generated byte cursor | Unchanged decoder used by both experimental conditions |
| Per-boundary harnesses and coverage exports | Pilot diagnosis and final measurement |
| `cell.py` | Equal-budget Rust-only campaigns |
| Combined corpus replay | Differential candidates from either condition |
| `c2r_campaign.py confirm` | Unchanged attribution and defect promotion |
| Corpus checkpoints | Execution/corpus-growth context |
| c2rust artifacts | Expected negative controls; any confirmed discrepancy still requires triage |

The current `snapshots.json` files record corpus size at checkpoints, not coverage at those
checkpoints. They must not be cited as proof that region coverage plateaued. The follow-up can
measure pilot coverage directly at its chosen checkpoint.

The API key is supplied only through `OPENAI_API_KEY`. It must not appear in a command-line
argument, prompt archive, log, plan, or committed file. The OpenAI SDK reads this environment
variable directly, as described by the
[official API quickstart](https://platform.openai.com/docs/quickstart/make-your-first-api-request).
The model is supplied through
`OPENAI_MODEL` and the exact returned model identifier is archived rather than using an
unrecorded “latest” alias.

## 5. Missing implementation pieces

### 5.1 Coverage diagnosis

Add `scripts/rq4/diagnose_input_domain.py`. For each boundary it should emit a compact JSON record:

* application and boundary name;
* matched/planned/built status;
* function and region coverage for that boundary's own campaign corpus;
* the relevant C function body and callees needed to interpret its guards;
* the current InputPlan entries and their evidence;
* conversions, guards, and constant-index reads involving fuzz-controlled values; and
* corpus size and artifact counts.

The diagnostic must use archived coverage exports where possible. If an old archive lacks the
generated `lib.rs` needed for line alignment, regenerate that harness from the recorded generator
version or mark the diagnostic unavailable; do not guess source coordinates.

The LLM is not shown translated Rust, known defects, divergence artifacts, or the defect manifest.
Its task is to improve the C-derived value distribution, not to tune around one translator.

### 5.2 Structured LLM response

Add `scripts/rq4/propose_input_hints.py`, using the Responses API with Structured Outputs. The
response schema should permit only records of this form:

```json
{
  "boundary": "ti_sma",
  "assignments": [
    {"path": "size", "c_type": "int", "value": 64},
    {"path": "options[0]", "c_type": "double", "value": 5.0}
  ],
  "evidence": [
    {"file": "sma.c", "line": 35, "claim": "options[0] is cast to the integer period"}
  ],
  "reason": "Exercise accepted periods and loop bodies"
}
```

The script makes five independent responses to one frozen prompt per selected application. Each
response may contain several seed cases. The experiment takes the deterministic union of all valid
cases; it does not choose the response with the best coverage. Duplicates are removed by the
boundary name and the sorted assignment paths and value bits. A global cap per boundary prevents
an unbounded seed corpus; when the cap is exceeded, cases are ordered by their canonical JSON and
truncated by a fixed rule recorded before the first call.

Archive the prompt, JSON schema, raw structured response, response ID, returned model identifier,
timestamp, token usage, request parameters, and hashes of every source input. Set `store=false` in
the request. Structured Outputs supplies machine-readable shape; the checks below decide whether a
well-shaped proposal is usable.

### 5.3 Deterministic hint validation

Add `scripts/rq4/validate_input_hints.py`. A hint is accepted only if:

1. the boundary and every assignment path resolve to the archived InputPlan;
2. every target is an existing scalar or a constant-index element of an existing scalar array;
3. every proposed value is representable by the declared C type;
4. every cited file and line exists and the cited line lies in the relevant C function or a
   directly included definition;
5. the same case resolves for every translated artifact of the application selected for the
   experiment; and
6. materializing and decoding the seed reproduces every proposed assignment exactly.

Evidence validation establishes provenance, not that the LLM's interpretation is correct. The
unchanged harness decoder is what prevents a wrong interpretation from changing the method.

### 5.4 Seed materializer and runner

Add `scripts/rq4/materialize_hint_seeds.py`. It consumes the lowered InputPlan, a validated hint
file, and a fixed pseudorandom seed. It emits one hinted seed and one paired control seed for each
semantic case. The first version supports bounded and unbounded scalars plus constant-index
elements of fixed-size scalar arrays; other layouts fail explicitly. Add round-trip regression
cases for a bounded scalar and for `ti_sma`'s `options[0]` offset.

Add `scripts/rq4/refinement_experiment.py` to build and run the paired conditions, archive their
corpora separately, invoke the existing coverage and replay machinery, and produce one result
record per artifact and seed.

## 6. Selecting cells

Selection happens after the current automatic chain is complete. Because the current results have
already been inspected, this is an explicitly **exploratory, feedback-guided extension**, not a
pre-registered confirmatory result.

An application is eligible when at least two of its translated artifacts satisfy all three
conditions under the automatic baseline:

1. built boundaries / matched boundaries is at least 0.80;
2. function coverage is at least 0.80; and
3. region coverage is at most 0.50.

These conditions identify a value-distribution gap: most boundaries build, most functions are
entered, and much of their internal code remains unexplored. Apply one C-derived hint set to every
available translated artifact of the selected application, including artifacts that individually
fall just outside a threshold. Never select individual translators based on whether refinement is
likely to help them.

With the currently completed cells, Tulip is the expected first case. PtrTrans cJSON and
C2SaferRust lil do not meet the construction/function conditions and should remain unchanged.
The final eligible set is computed once after the full baseline table is frozen.

## 7. Execution protocol

### Milestone A: ten-minute proof of mechanism

Run baseline and hinted harnesses for Tulip c2rust for ten minutes each with the same fresh seed.
This milestone checks that:

* hint generation, validation, and seed materialization are end to end;
* round-trip decoding recovers the proposed semantic assignments;
* the hinted campaign enters accepted option domains more often;
* combined replay and confirmation still run unchanged; and
* region coverage can be measured from both corpora.

Stop the extension if the mechanism does not improve any target boundary or if the implementation
requires changing storage, bridges, or the oracle. A failed pilot is retained as a result.

### Milestone B: held-out paired comparison

For every eligible application and all of its available artifacts, run both conditions:

* **Automatic:** frozen planner and original decoder, seeded with the size-matched control corpus.
* **Automatic + LLM hints:** the same binary, decoder, planner, and oracle, seeded with the
  plan-materialized hint corpus.

Use seeds 43, 44, and 45. Each condition receives the same one-hour wall-clock budget, initial
fixed corpus, `max_len`, machine allocation, and campaign flags. Alternate condition order across
seeds to reduce time-order effects. The existing seed-42 campaigns are pilot evidence and are not
included in this paired comparison. Corpora from the automatic, pilot, and hinted conditions are
never merged.

Every final corpus goes through the existing Rust-only coverage export, combined replay, and
confirmation pipeline. Candidate counts and defects are recorded, but neither is used to choose or
discard a hint set.

## 8. Measurements and reporting

The primary outcome is the paired absolute change in region coverage for each artifact and seed.
Secondary outcomes are:

* function-coverage change;
* number and fraction of accepted hints;
* number of boundaries affected by at least one hint;
* C-side `ub-gated` and confirmation verdict distributions;
* corpus size and executions per second;
* API calls, input/output tokens, wall time, and estimated API cost; and
* any confirmed defects, reported through the existing RQ2 manifest rather than counted as
  coverage gains.

Report every eligible artifact, including zero and negative changes. Show the automatic baseline
beside the hinted condition. A compact paper table is sufficient:

| Application / translator | Automatic region | + hints region | change | accepted hints |
|---|---:|---:|---:|---:|

For multiple fuzzing seeds, report the three paired values and their median; with so few seeds, do
not attach significance claims. The automatic RQ4 table remains the answer for the core method.
If the extension succeeds, present it as a component or follow-up experiment showing that
definition-derived LLM feedback can improve semantic-domain sampling. If it does not, retain the
result as evidence that the remaining gap requires richer construction or feedback.

## 9. Acceptance criteria

The implementation is ready for the full comparison when:

1. harness generation remains byte-for-byte identical on the harness regression suite;
2. hint output passes strict JSON-schema and deterministic semantic validation;
3. the exact same application-level hint file is used across translators;
4. round-trip checks show that every seed decodes to the assignments recorded in its hint case;
5. the paired initial corpora contain equal numbers and sizes of seeds, differing only at the
   plan-resolved assignment bytes;
6. any confirmed c2rust discrepancy is fully triaged before the full comparison proceeds; a real
   defect is retained rather than treated as a failed refinement;
7. results are reproducible from archived prompts, responses, hint files, hashes, seeds, and
   commands; and
8. the repository contains no API key or other credential material.
