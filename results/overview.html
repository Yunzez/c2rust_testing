Research overview · for a general audience

Testing C → Rust translations

Old C code is being auto-translated to Rust (a safer language) by tools like c2rust. Our question: did the translation keep the same behavior? If not, that's a bug hiding in supposedly-safe code.

1. The basic idea: give both versions the same test

Run the original C and its Rust translation on the same inputs, and compare the answers. If they ever disagree, the translation may be wrong. We do this automatically at massive scale with fuzzing (throwing millions of random inputs).
Like giving the same exam to the original and the copy, and checking every answer that differs.

2. Why it's not that simple — two traps

Trap A — we can't assume c2rust is correct.
It's the very thing we're testing. If we treat its output as "the right answer," we can never find its mistakes. So we have no trusted reference to compare against.
Trap B — not every difference is a bug.
Most disagreements are false alarms: the input was meaningless (see below), or we tested the code in the wrong place. Drowning in false alarms makes real bugs invisible.
The biggest source of false alarms: "undefined behavior" (UB). The C language leaves some operations undefined — e.g. a number overflowing, or reading past the end of an array. On those inputs there is no correct answer, so if C and Rust differ, it proves nothing about the translation. These are trick questions with no right answer — a disagreement there is not the translator's fault.

3. The core dilemma

We must catch real translation bugs — without trusting c2rust to be correct (Trap A), and without mistaking undefined-behavior noise for bugs (Trap B).

These pull in opposite directions: be strict and you flag everything (false alarms); be lax and you trust the tool you're supposed to check. The resolution is not a smarter bug filter — it's choosing where to test.

4. Our idea: test at the right place, not everywhere

A program is a tree of functions calling each other. The trick is to pick the right altitude to test — where inputs are constructible, no UB is triggered, and a difference would be a real bug. We call this the STU frontier. Goldilocks-style:
top API report(...) too high — also runs unrelated risky code → false alarms
  └─ middle safe_ratio(...) just right ✓ — sets up valid inputs for what it calls
      └─ helper scale(...) too low — alone, its assumptions break → false alarms

A static analysis (no running needed) scores each function on these rules and picks the middle layer. Then we fuzz only there, and only count differences on UB-free inputs — so a surviving difference is a genuine translation bug.

Picking the right boundary beats the naive strategies — in a controlled test it is the only strategy that is both clean (no false alarms) and still catches a deliberately-planted real bug✓
Works on real-world libraries (musl C library, base64, a regex engine, big-number arithmetic)✓
Rigorous: we report zero "bugs" that are really UB noise — matching the strict standard from compiler testing✓

Honest note: c2rust turns out to be faithful on our programs (it's built to copy behavior exactly, including flaws), so it yields no real bugs — which is the expected, correct outcome and confirms our method doesn't cry wolf. We are now extending the same method to a second, riskier tool (a "safety lifter" that rewrites the Rust to be safer, where behavior can actually change) — to show the approach generalizes and to find bugs that matter.

7. In one sentence

We're not predicting "which function has a bug." We're solving where it's even valid to test a translation — so that a difference between C and Rust is trustworthy evidence, not noise.
